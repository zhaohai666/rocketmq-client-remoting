## 顺序消费「顺序消费保序」偶发 0/10 —— 根因定位并修复（非 sleep 窗口问题）

之前日志里把「顺序消费 0/10」归因为「30s pull 超时超过消费者 sleep 窗口，加大 sleep 即可」是**误诊**。
真实根因：**消费循环在单线程内顺序长轮询各队列**（`_consume_loop` → `_pull_and_consume_once`），
每个空闲队列的 suspend 长轮询会阻塞整轮。顺序消息全部落在单队列（如 qid=2，selector 路由确定），
排在前的空闲队列（qid=0/1）的 15~20s 阻塞把满载队列饿死，固定 sleep 窗口内根本轮不到 qid=2 → 0 条。
Tag/Prop 之所以稳定，是因为消息 round-robin 分散到多个队列，靠前队列就有消息。

### 修复（已验证 11/11 且连续两次稳定）
1. `consumer.py`：`DefaultMQPushConsumer.__init__` 新增两个可调旋钮
   `pull_timeout_millis`(客户端等响应, 默认 30000) 与 `pull_suspend_timeout_millis`(服务端挂起, 默认 15000)，
   并把 `_pull_and_consume_once` 中 `pull_message(...)` 的硬编码 `timeout_millis=30000` / `suspend_timeout_millis=15000`
   改为引用这两个属性。
2. `consumer.py`：`RemotingTimeoutException`（长轮询超时）按**良性 debug** 处理（不记 ERROR），因为 broker 会
   把下发的 suspend 钳制到自身 `brokerSuspendMaxTimeMillis`（默认 ~15s），空闲队列周期性超时是正常行为，
   记 ERROR 只会污染客户端运行日志（`rocketmq/logging.py` 落 `~/logs/rocketmqlogs/rocketmq_client.log`）。
3. `verify_message_types.py`：`run_consumer` 改「活跃等待直到收到 expect 条（或最多 duration 秒）」而非盲 sleep；
   并设置短超时 `pull_timeout=3000, pull_suspend=1000`，让空闲队列 ~1s 即轮转，循环很快到达满载队列。

### 验证

### 本轮新踩的坑（值得记住）
1. **`TopicPublishInfo` 不可拷贝**：内含 `std::atomic<uint64_t>` 轮询游标。它的游标是**跨调用共享
   状态**（Java ThreadLocal / Python 缓存单例），所以 `getTopicPublishInfo()` 必须返回
   `std::shared_ptr<TopicPublishInfo>`。曾按值返回 + 内含 `std::mutex` → 编译期
   "call to implicitly-deleted copy constructor"；就算去掉 mutex 改为可拷贝，也会退化成
   "每次发送都从 0 号队列重来"，轮询失效。
2. **`RemotingException` 需显式 include** `rocketmq/remoting/exception.h`；`mq_client.h` 只前向到
   `remoting_client.h`，不传递异常类型。producer.cpp / mq_client.cpp 都漏过一次。
3. **`CreateTopicRequestHeader` 原来不存在**：`UPDATE_AND_CREATE_TOPIC` 需要它，字段照 Java
   （topic/defaultTopic/readQueueNums/writeQueueNums/perm/topicFilterType/topicSysFlag/order/attributes/force）。
4. **`Message::isBatch` 是必需的显式字段**：broker `SendMessageProcessor` 靠
   `requestHeader.isBatch()` 决定 `sendBatchMessage` 还是 `sendMessage`；`Message` 非多态（无虚函数）
   不能用 `dynamic_cast` 判断，故在 `Message` 上加 `bool isBatch`，由 `MessageBatch::generateFromList` 置位。
5. **`buildClientId()` 带 pid + 原子序号**：Java 是 `ip@instanceName@unitName(pid派生)`，Python 是
   `instanceName@时间戳`。同秒内连续起多个 consumer 时时间戳会撞（broker 消费组 channel 表以
   clientId 为键，撞了互相顶掉），故加 pid 与进程内序号。

## Java 侧压缩机制核查（并发现 Python 一个真 bug）

问题：Java 实现了自动压缩吗？**答：是，生产端全自动、全路径。**

- 触发点：`DefaultMQProducerImpl.sendKernelImpl` L945 → `tryToCompressMessage` L1112。
  条件 `body.length >= compressMsgBodyOverHowmuch`（默认 **4096**，即 4KB）；**`MessageBatch` 直接
  return false**（批量消息不压缩）。
- 命中后：`compressor.compress(body, compressLevel)` 替换 body，并
  `sysFlag |= COMPRESSED_FLAG; sysFlag |= compressType.getCompressionFlag();`（L945-948）。
- 配置项（`DefaultMQProducer`）：`compressMsgBodyOverHowmuch`(4096) /
  `compressType`（系统属性 `rocketmq.message.compressType`，默认 **ZLIB**）/ `compressLevel`
  （系统属性 `rocketmq.message.compressLevel`，默认 5）。`CompressorFactory` 有 LZ4/ZSTD/ZLIB 三实现。
- `sendKernelImpl` 是**唯一内核**：调用点覆盖 SYNC(L1243) / ASYNC(L1283,1749,1793) / ONEWAY(L1310) /
  顺序(L1360) / 主发送循环(L789)，所以压缩是**全自动且对所有发送路径生效**。
- 消费端自动解压：`MessageDecoder.decode(..., deCompressBody)` L520-524，按类型解压后
  `sysFlag &= ~COMPRESSED_FLAG`（保留类型位）。

### ⚠️ 顺带查出：Python `_decompress` 少了 Java 的向后兼容映射（真 bug）
Java `MessageSysFlag.getCompressionType` → `CompressionType.findByValue((flag & 0x700) >> 8)`，
而 `findByValue(0)` **返回 ZLIB**，源码注释："To be compatible for older versions without compression type"。
即**没有类型位的老压缩消息，Java 按 ZLIB 正确解压**。

Python `_decompress` 只判断 `== LZ4_TYPE(1)` / `== ZLIB_TYPE(3)`，**其余（含 0）原样返回 body**，
但外层**仍旧执行了 `clear_compressed_flag`** → 返回压缩字节流 + 标志位被抹掉 = **静默损坏且事后不可察觉**。

实测（临时脚本 `/tmp/zip_type0_check.py`，按 `test_compressed_message_roundtrip` 的布局手工构造 17 段报文）：

| sysFlag 类型位 | 解出长度 | 期望 | body 还原 | 解码后 sysFlag |
|---|---|---|---|---|
| 3 (ZLIB) | 550 | 550 | ✅ | 0x300 |
| **0（旧版无类型位）** | **25** | 550 | ❌ | **0x0**（标志被清） |

修法（3 行，对齐 Java）：`_decompress` 中把 `0` 视同 `ZLIB_TYPE`。
(`_compress` 无需改，本仓库生产端不压缩。)
