  `MQClientInstance::registerRPCHook` 转发，**first-wins**。
- **.NET**：新增 `Remoting/RpcHook.cs`（BCL `HMACSHA1` + `Convert.ToBase64String`，**零 NuGet**）；

### ⚠ 本轮最贵的一个坑（写进了三个 harness 的注释）
真机脚本里 S4/S5 原来写成"**先发 3 条、再起消费者**"，结果同一场景三语言结果不一致：
Python 收 0 条、C++/.NET 收 3 条。**不是客户端 bug**，是两个叠加效应：
1. Java 默认 `CONSUME_FROM_LAST_OFFSET`：新消费组首次消费且无已提交位点时，初始位点 =
   该队列**当时的** maxOffset（`RebalancePushImpl.java:174-190`）→ 已存在的消息本来就收不到；
2. broker 的 consumequeue 是**异步分发/刷盘**的，"刚发完立刻查 maxOffset"可能读到 **0**
   （探针 v1 实测读到 0，探针 v2 隔一会儿读到正确的 1/1/1/0）→ 谁先解析位点决定了读到 3 还是 0。
→ 结论：**测消费必须"先起消费者再发消息"**，否则是"正确但测不出东西"的假失败。
排查用的两个探针保留在 `/tmp/probe_offset.py`、`/tmp/probe_offset2.py`

（`probe_offset2` 值得留：F 打原始 extFields 证明 GET_MAX_OFFSET 解析正确、D/E
分别验证"先起消费者→收 3 条"和"先发→收 0 条"）。

## Request-Reply（P2）三语言完成并推送（提交 56350c2 [Py+C++] / 8932727 [.NET]，已 push origin/main）

- **协议链路（照 Java 5.5.1 复刻）**：请求方 `request(msg, timeout)` 写 CORRELATION_ID(uuid)/
  REPLY_TO_CLIENT(本端 clientId)/TTL → 发送；应答方普通 push 消费者 `createReplyMessage` +
  `producer.send(reply)`（MSG_TYPE=="reply" 时请求码选 **SEND_REPLY_MESSAGE_V2(325)**）；
  broker 按 REPLY_TO_CLIENT 反查 channel，用 **PUSH_REPLY_MESSAGE_TO_CLIENT(326)** 推回请求方，
  客户端按 CORRELATION_ID 从进程单例 RequestFutureHolder **先原子 remove 再填充**投进等待槽。
- **C++ 传输层改造**：`registerProcessor` 的回调签名升级为可返回
  `std::optional<RemotingCommand>`（opaque 必须原样带回；oneway 请求不回响应），
  新增 `sendResponseByAddr`（按地址查已有连接写回，**不新建连接**）。
  326 处理器是**客户端实例级**（Python 在 MQClientInstance 构造器注册；C++ 同构造器注册；
  .NET 在 MqClient 构造器），回调在读线程上跑、**绝不 invokeSync**。
- **坑：326 必须回响应**——broker 侧 Broker2Client.callClient 是 invokeSync(10s)，不回它会记
  "push reply message fail"；查不到等待槽（迟到/重复应答）也回 SUCCESS 只记 warn。
- **坑：发送失败要三件事**——sendRequestOk=false + putResponseMessage(空)唤醒 + 记 cause，
  否则等待方白等满 timeout（三侧一致）。
- **坑：clientId 撞名**会把 broker 的应答推到错误连接上（C++ buildClientId 带 pid+seq 无碰撞）。
- **坑：`<cluster>_REPLY_TOPIC` 是 broker 预注册系统 topic**，客户端 createTopic 被
  INVALID_PARAMETER(29)「conflict with system topic」拒绝且 broker 无日志；
  C++ createTopic 会把 broker 错误包成 MQClientException（消息里带 CODE/DESC，无 cause 链可解）。
- **单测**：pytest 172 passed（新增 16，test_logging_config 的 2 个 error 是沙箱 tmpdir EEXIST
  环境噪音）；ctest **10/10**（新增 rmq_test_request_reply）；xunit **71/71**（新增 16）。
- **真机**（`/tmp/run_rr_live.sh python|cpp|dotnet|all`，S1–S7）：Python **16/16**、C++ **15/15**、
  .NET **16/16**，RC=0。S4 用独立 watcher 订阅 DefaultCluster_REPLY_TOPIC 证明应答走了 325 落盘

- 有意差异（三侧一致）：不实现 Java 的 scanExpiredRequest 后台清理线程（request 的 finally +
