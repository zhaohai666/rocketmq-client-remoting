## 事务消息：三侧统一对齐 Java 两阶段（进行中）

用户要求「事务消息需要对齐 Java 的，其他语言也是」→ C++ / Python / .NET 三侧同时把简化单阶段
改为 Java 语义的两阶段（半消息 + 本地事务 + END_TRANSACTION + broker 回查）。

### Java 协议事实（已逐条核对 zhaohai666-rocketmq 源码，勿再猜）
- `DefaultMQProducerImpl.sendMessageInTransaction`（client/.../DefaultMQProducerImpl.java L1433-1509）：
  - 属性 `TRAN_MSG=true`、`PGROUP=<producerGroup>`；`send()` 时 sendKernelImpl（L951-953）检测
    `TRAN_MSG` → `sysFlag |= TRANSACTION_PREPARED_TYPE`。
  - 初始 state=UNKNOW；SEND_OK 才执行本地事务（返回 null→UNKNOW，抛异常记 localException）；
    FLUSH_DISK_TIMEOUT / FLUSH_SLAVE_TIMEOUT / SLAVE_NOT_AVAILABLE → ROLLBACK。
  - 末尾无条件 `endTransaction(...)`（异常只 warn 不抛）。
- `endTransaction`（L1528-1568）：`id = decodeMessageId(offsetMsgId ?: msgId)`；
  `commitLogOffset = id.offset`；`tranStateTableOffset = sendResult.queueOffset`；
  `msgId = sendResult.msgId`；commitOrRollback = COMMIT 8 / ROLLBACK 12 / UNKNOW 0；
  走 `endTransactionOneway` → **RequestCode 37，oneway**。
- 回查：**RequestCode 39**。broker `Broker2Client.checkProducerTransactionState`（L74-88）
  把 `MessageDecoder.encode(messageExt, false)` 放进 body，用 **invokeOneway(10ms)** 发给客户端；
  客户端 `ClientRemotingProcessor.checkTransactionState`（L95-127）解码 header + body 得到
  MessageExt，按属性 `PGROUP` 选 producer，**返回 null 即不回响应**。
- `DefaultMQProducerImpl.checkTransactionState`（L366-430）在**新线程**执行
  `listener.checkLocalTransaction(msgExt)`，再发一个
  `END_TRANSACTION(fromTransactionCheck=true, commitLogOffset/ tranStateTableOffset 取自回查 header,
  msgId = UNIQ_KEY ?: msgId)`。
- **键名 = Java 字段声明名**（`RemotingCommand.makeCustomHeaderToNet` L430-456 用反射
  `field.getName()`）。⚠ 所以是 **`bname` 而不是 `brokerName`**（父类 RpcRequestHeader 的字段
  `protected String bname;`，Java setter 叫 setBrokerName）。写错 broker 静默丢字段。
- 常量：END_TRANSACTION=37、CHECK_TRANSACTION_STATE=39；
  TRANSACTION_NOT_TYPE=0 / PREPARED=0x1<<2=4 / COMMIT=0x2<<2=8 / ROLLBACK=0x3<<2=12；
  MessageConst: TRAN_MSG / PGROUP / UNIQ_KEY。

### 三侧改造的共同形状
1. Header：EndTransactionRequestHeader 补 `topic`+`bname`；新增 CheckTransactionStateRequestHeader
   （topic/tranStateTableOffset/commitLogOffset/msgId/transactionId/offsetMsgId/bname）。
2. RemotingClient：新增「按 requestCode 注册处理器」；dispatch 时若 **不是响应类型且在途表里查不到
   opaque** → 交给处理器（Java 不回响应）。
3. Producer：两阶段 sendMessageInTransaction + 私有 endTransaction + checkTransactionState
   （新线程）+ 启动时注册回查处理器。

### 真机验证要点
- broker 配置缩短回查等待：`transactionCheckInterval=3000`、`transactionTimeOut=3000`、
  `transactionCheckMax=5`。
- 三场景：COMMIT 应被消费 / ROLLBACK 等 6s 仍不被消费 / UNKNOW+回查最终被消费且
  **用计数器证明 checkLocalTransaction 被调用过**。
- 起集群后 `sleep 12` 等 broker 向 NS 注册（端口开 ≠ 已注册）。

### 关键根因与修复（三侧同构）
1. **PROPERTY_PRODUCER_GROUP 字面值错误**（三侧全是 "PRODUCER_GROUP"）→ 改 "PGROUP"。
2. **CheckTransactionStateRequestHeader.offsetMsgId 写成整型**（C++/Python 的旧定义、.NET 的 long?）→ Java 是 String。
3. **EndTransactionRequestHeader 缺 topic/bname**（键必须是 bname，不是 brokerName）。
4. **生产者从不发心跳** → broker 找不到回查 channel，UNKNOW 永不回查。三侧都补了心跳线程（ProducerHeartbeatThread，30s 周期，含 ProducerData，fingerprint=0）。
5. **RemotingClient 需支持 broker 主动请求**：三侧都新增 register_processor/registerProcessor；dispatch 判定"非响应类型且不在途表"→ 处理器；处理器在读线程执行必须 try/catch。
6. **.NET 特有**：DelayTimeLevel getter 对缺失键返回 0，事务的延迟校验必须查 Properties 字典否则恒触发。
7. **Python 特有**：MessageConst 缺 TIMER_* 常量（用 getattr 兜底）；SimpleMessageListener 回调参数是**列表**不是单条。
8. 验证脚本消费者必须**先于发送启动**，否则错过投递（消费从最新位点开始）。
