## 事务消息：三侧统一对齐 Java 两阶段（进行中）

用户要求「事务消息需要对齐 Java 的，其他语言也是」→ C++ / Python / .NET 三侧同时把简化单阶段
改为 Java 语义的两阶段（半消息 + 本地事务 + END_TRANSACTION + broker 回查）。

### Java 协议事实（已逐条核对 zhaohai666-rocketmq 源码，勿再猜）
- `DefaultMQProducerImpl.sendMessageInTransaction`（client/.../DefaultMQProducerImpl.java L1433-1509）：
  - 属性 `TRAN_MSG=true`、`PGROUP=<producerGroup>`；`send()` 时 sendKernelImpl（L951-953）检测
    `TRAN_MSG` → `sysFlag |= TRANSACTION_PREPARED_TYPE`。
  - 初始 state=UNKNOW；SEND_OK 才执行本地事务（返回 null→UNKNOW，抛异常记 localException）；
    FLUSH_DISK_TIMEOUT / FLUSH_SLAVE_TIMEOUT / SLAVE_NOT_AVAILABLE → ROLLBACK。
  - 末尾无条件 `endTransaction(...)`（异常只 warn 不抛）。
- `endTransaction`（L1528-1568）：`id = decodeMessageId(offsetMsgId ?: msgId)`；
  `commitLogOffset = id.offset`；`tranStateTableOffset = sendResult.queueOffset`；
  `msgId = sendResult.msgId`；commitOrRollback = COMMIT 8 / ROLLBACK 12 / UNKNOW 0；
  走 `endTransactionOneway` → **RequestCode 37，oneway**。
- 回查：**RequestCode 39**。broker `Broker2Client.checkProducerTransactionState`（L74-88）
  把 `MessageDecoder.encode(messageExt, false)` 放进 body，用 **invokeOneway(10ms)** 发给客户端；
  客户端 `ClientRemotingProcessor.checkTransactionState`（L95-127）解码 header + body 得到
  MessageExt，按属性 `PGROUP` 选 producer，**返回 null 即不回响应**。
- `DefaultMQProducerImpl.checkTransactionState`（L366-430）在**新线程**执行
  `listener.checkLocalTransaction(msgExt)`，再发一个
  `END_TRANSACTION(fromTransactionCheck=true, commitLogOffset/ tranStateTableOffset 取自回查 header,
  msgId = UNIQ_KEY ?: msgId)`。
- **键名 = Java 字段声明名**（`RemotingCommand.makeCustomHeaderToNet` L430-456 用反射
  `field.getName()`）。⚠ 所以是 **`bname` 而不是 `brokerName`**（父类 RpcRequestHeader 的字段
  `protected String bname;`，Java setter 叫 setBrokerName）。写错 broker 静默丢字段。
- 常量：END_TRANSACTION=37、CHECK_TRANSACTION_STATE=39；
  TRANSACTION_NOT_TYPE=0 / PREPARED=0x1<<2=4 / COMMIT=0x2<<2=8 / ROLLBACK=0x3<<2=12；
  MessageConst: TRAN_MSG / PGROUP / UNIQ_KEY。

### 三侧改造的共同形状
1. Header：EndTransactionRequestHeader 补 `topic`+`bname`；新增 CheckTransactionStateRequestHeader
   （topic/tranStateTableOffset/commitLogOffset/msgId/transactionId/offsetMsgId/bname）。
2. RemotingClient：新增「按 requestCode 注册处理器」；dispatch 时若 **不是响应类型且在途表里查不到
   opaque** → 交给处理器（Java 不回响应）。
3. Producer：两阶段 sendMessageInTransaction + 私有 endTransaction + checkTransactionState
   （新线程）+ 启动时注册回查处理器。

### 真机验证要点
- broker 配置缩短回查等待：`transactionCheckInterval=3000`、`transactionTimeOut=3000`、
  `transactionCheckMax=5`。
- 三场景：COMMIT 应被消费 / ROLLBACK 等 6s 仍不被消费 / UNKNOW+回查最终被消费且
  **用计数器证明 checkLocalTransaction 被调用过**。
- 起集群后 `sleep 12` 等 broker 向 NS 注册（端口开 ≠ 已注册）。

- .NET：xunit 46/46；`rmq redelivery` 13/0（gap=10.1s）

### 架构级改造（三侧同构）
**拉取-缓冲-分发三层**：原先"单线程串行长轮询"会让空闲队列的 suspend 长轮询阻塞满载队列（饿死）。改为：每队列一个拉取线程（并行长轮询）+ 每队列 pending deque + 独立分发线程；offset 拆成「拉取游标」与「消费位点」两条线。

### 关键修复
1. **回投接线**：RECONSUME_LATER/异常批次 → 已存在的 sendMessageBack 进 %RETRY%（delayLevel=0 时取 3+reconsumeTimes），offset 按 ackIndex 推进。
2. **位点持久化**：每 5s UPDATE_CONSUMER_OFFSET(15) 提交消费位点；启动 QUERY_CONSUMER_OFFSET(14) 兜底；shutdown 补交。广播模式改走本地文件 $HOME/.rocketmq_offsets/。
3. **顺序锁**：LOCK_BATCH_MQ(41)/UNLOCK_BATCH_MQ(42) 每 20s，只消费 lockOK 队列；shutdown 解锁。
4. **广播模式**：全队列本地消费 + 本地 offset 落盘 + 失败不回投。
5. **流控**：pending ≥ pullThresholdForQueue(默认1000) 跳过拉取，暴露触发计数器。

### 踩坑记录
- **RECONSUME_TIMES 属性键是单数 `RECONSUME_TIME`**（Java MessageConst），且重投次数主要走 MessageExt 线上格式第13字段（getReconsumeTimes()），listener 侧判断要用后者。
- Python `MQBrokerException.UNKNOWN` 属性不存在（旧死分支），pull 异常分支会 AttributeError 杀循环 —— 已删。
- Python `SimpleMessageListener` 回调参数是**列表**；消费者必须**先于发送启动**。
- 盘点修正：Python 侧 `MessageListenerOrderly` 早已存在（之前盘点漏看），缺的是接线与 broker 锁。
- 联调脚本：/tmp/run_redelivery_live.sh [cpp|python|dotnet|all]。

### 真机新增场景

- 全部：`PASS=21 FAIL=0`。

### 关键根因（都靠诊断脚本定位，不是猜）
1. **消费者路由绝不能兜底**：`update_topic_route_info_from_name_server` 原来对任何拉不到的 topic 都用 TBW102 合成路由并**落库**。`%RETRY%group` 在首次回投前不存在 → 被合成出一组"假队列"，两个实例在不同时刻拉取得到不同队列数 → rebalance 视图不一致。Java 的 `isDefault` 兜底**只在生产者路径**（`DefaultMQProducerImpl:905`），消费者永远拉真实路由。
2. **撤销队列必须收尾**：队列被 rebalance 撤走时原来只删线程，不 persist 位点、不丢 pending。**尤其**：长轮询期间被撤销的队列，pull 返回后原代码会**重建 pending 缓冲**并把在途消息交给 listener → 与新属主重复消费（S6 曾多出 4 条重复）。已在 `_queue_pull_loop` 与 `_dispatch_loop` 两处加"锁内重判所有权"（对齐 Java `ProcessQueue.isDropped()`）。
3. **初始位点必须在分配时解析**：原来留到首次拉取才惰性解析，而 `CONSUME_FROM_LAST_OFFSET` 语义是"**分配时刻**的最新位点"→ 分配后新产生的消息被全部跳过。真机症状：消费者有 5 个队列、topic 里有消息，却一条都收不到。对齐 Java `updateProcessQueueTableInRebalance`（新队列 → `computePullFromWhereWithException` → `offsetStore.updateOffset`）。另补：`%RETRY%` 主题首次消费且无已提交位点时从 **0** 开始（Java `RebalancePushImpl:181`）。
4. **测试脚本的顺序陷阱**：`CONSUME_FROM_LAST_OFFSET` 下消费者必须**先于发送**启动，否则消息被跳过（S8 首次失败就是这个，不是实现问题）。
5. **心跳时序**：消费者在 start 时发一次心跳，但此时若 topic 还没路由，心跳根本发不出去（没有 broker 地址），下一次要等 30s（Java 同样）。所以"消费者先于 topic 存在启动"这种用法本来就要等 ~30s；真实验证应先建 topic（脚本里 `prepare_topic`）。

### 命名空间（原来只是死标志）
Java 包装点：`DefaultMQProducer` 每个 `send*` 公开入口 `msg.setTopic(withNamespace(...))`；`DefaultMQProducer.start:375` 包生产者组；`DefaultMQPushConsumer.subscribe:838` 包 topic、`start:763` 包消费组。分隔符 `%`，`%RETRY%NS%GID` 形式（retry 前缀在命名空间之外）。系统资源（`rmq_sys_`/`CID_RMQ_SYS_`）不包。已新建 `python/rocketmq/remoting/protocol/namespace_util.py`（wrap/without/wrapNamespaceAndRetry/getNamespaceFromResource 全套）。

### 其余小项
- 路由周期刷新：`MQClientInstance` 30s 刷新"在用 topic"（Java `pollNameServerInterval`）。
- 启动 1 分钟内且**当前无任何分配**时 rebalance 间隔降为 2s（Java 固定 20s，这是有意的偏离，避免消费者先于 topic 创建启动时长时间不消费；60s 后回落到 20s 以免长期高频打 NS）。

### .NET 真机暴露的两个致命坑（已修，真机 17/0 复验通过）
1. **读线程自死锁**：`OnConsumerIdsChanged` 原来在 remoting **读线程**上直接 `DoRebalance()`，
   内部分阻塞 `invokeSync(GET_CONSUMER_LIST_BY_GROUP)` → 读线程卡 5s 超时、连带心跳超时、首轮分配只剩
   `%RETRY%` 1 队列。改为**只置标志**（`_rebalanceNow.Set()`），与 C++/Java 一致。
2. **TOCTOU 进程崩溃（Abort trap: 6 / RC=134）**：`Shutdown()` 先置 `_started=false`、稍后才 join pull
   线程；窗口内 `RebalancePullThreads` 起的 pull 线程第一条语句 `Client()` 抛 `consumer not started`，
   而 .NET **后台线程未处理异常会终止整个进程**（Java/C++/Python 只让该线程退出）。三层修复：
   - `MakeThread` 包 try/catch 记 WARN（降级为单线程退出）；
   - `QueuePullLoop` 开头用 `MQClientInstance? clientRef = _mqClient; if (clientRef is null || !_started) return;` 替代 `Client()`；
   - `RebalancePullThreads` 起线程前 `if (_stop || !_started) return;`。
