### 二、最贵的一个认知纠正：`POP_CK` 是**客户端**写的，不是 broker 写的

- **普通 topic 直连 POP 时消息上没有任何 POP_CK 属性**（探针实测 props 只有
  `MSG_REGION/UNIQ_KEY/CLUSTER/KEYS/WAIT/TRACE_ON`）—— 我差点据此误判"POP 不可用"。
- broker 只在 **retry-topic 重编码路径**才写（`PopMessageProcessor.java:849` 的 `putIfAbsent`）。
- 普通 topic 的 CK 串必须由**客户端** `MQClientAPIImpl.processPopResponse`（`:1150-1225`）
  用响应头的 `startOffsetInfo` / `msgOffsetInfo` 反构：
  按 `topic@queueId` 取 startOffset → 按 queueOffset 在同队列 offset 列表里求 index 取
  msgQueueOffset → `buildExtraInfo(...)` 拼 **8 段**（空格分隔）。**没有它就无法 ACK。**
- 反构完还要补 `1ST_POP_TIME`（仅当缺失，值 = popTime）。
- 查表 key 的坑：`buildQueueOffsetSortedMap` 用的 retryFlag 在"消息已带 POP_CK"时取自
  **POP_CK 第 5 段**，否则由**消息 topic** 推断（broker 可能改写 topic）。

### 三、其他关键协议事实

- `bornTime` 必须填**当前毫秒时间戳**：broker 用 `now - bornTime - pollTime > 500` 判定
  "超时太久"直接回 `POLLING_TIMEOUT(210)`（`PopMessageRequestHeader:135`）。
- `maxMsgNums > 32` → INVALID_PARAMETER；`queueId >= readQueueNums` → INVALID_PARAMETER；
  `queueId = -1` 表示弹所有队列；`initMode` 0=MIN / 非 0=MAX。
- **ACK 的 `offset` 是 consumeQueue offset**（CK 第 8 段），不是 commitlog offset。
  实测非法 queueId → `MESSAGE_ILLEGAL(13)`，越界 offset → `NO_MESSAGE(208)`。
- 响应码映射：SUCCESS→FOUND；POLLING_FULL(209)→POLLING_FULL；
  POLLING_TIMEOUT(210)/PULL_NOT_FOUND(19)→POLLING_NOT_FOUND；其它抛异常。
- `CHANGE_MESSAGE_INVISIBLETIME` 返回**新的** popTime/invisibleTime/reviveQid，
  客户端要用新值重建 extraInfo 再 ACK（Java `MQClientAPIImpl:1025-1028`）。
- 本仓 5.5.1 **不存在** `INVISIBLE_TIME` / `POP_CORRELATION_ID` / `POP_SKIP_ACK` 这些
  属性常量（grep 0 命中），属 gRPC/Proxy 概念，直连 remoting 不要去找。
- 复活：ck 的 `reviveTime = popTime + invisibleTime` 到点且未全 ack → 重投到
  `%RETRY%<group>_<topic>`（V1，`_`；V2 用 `+`，`enableRetryTopicV2` 默认 false）。

**踩到并修掉的两个「静默失败」级 bug**（三侧同源，Python 先发现后两侧照搬）：

1. **`ackIndex` 默认值**：Java `ConsumeConcurrentlyContext.ackIndex = Integer.MAX_VALUE`
   （= 全 ack），而本项目默认 **-1**（push 回投路径的语义）。照搬 -1 会让
   `CONSUME_SUCCESS` **一条都不 ack**，整批在 invisibleTime 后复活重投。
   修法：POP 路径构造 context 时把 ackIndex 置为 `size-1`。
2. **档位表单位是秒**，`CHANGE_MESSAGE_INVISIBLETIME` 要毫秒。

即使 ack 完全没发出去，消息也还没到复活时间，看着照样"全过"。已把
`popInvisibleTime` 压到 10s、观察窗口拉到 16s（**观测窗口必须 > invisibleTime**），
这才真正锁住。**凡是"验证不重复投递"的断言，观察期一定要长于复活周期。**

**一处有意偏离 Java**：`checkNeedAckOrDelay` 对"存活时间小于首档"的消息会算出
`delayLevel = -1`，Java 随后索引 `delayLevelTable[-1]` 抛 AIOOBE。三侧都钳到首档。

调试过程中的两个非代码坑（记一下，省得再踩）：
- `SimpleMessageListener` 的回调签名是 **`fn(msgs)` 单参**，不是 `(msgs, context)`；
  写成两参会抛 TypeError，而 POP 消费循环把 listener 异常**按 RECONSUME_LATER 吞掉**

## CheckForbiddenHook / FilterMessageHook + 订阅语义对齐 Java（三语言收官）

### 一、顺手修掉一个此前一直错着的订阅语义（三侧同源偏差）
`FilterAPI.buildSubscriptionData` 原先：`"*"` → `tagsSet={"*"}`、从不填 `codeSet`。用 Java 探针
（`/tmp/subprobe/SubProbe.java` 等）实测真实语义是：
- `null` / `""` / `"*"` → `subString` 归一 `"*"`，**tagsSet 与 codeSet 都保持空**；
- 显式 tag → `tagsSet={tag}` **且** `codeSet={tag.hashCode()}`（Java `String.hashCode`，需新实现
  带 int 回绕的 `java_string_hash`）；
- `"   "`（纯空白）**不早返回**，走 split 路径；`"||"` 抛 `Exception("subString split error")`。

两个偏差各有真实后果：塞 `"*"` 会让「订阅全量」时**客户端二次 tag 过滤**把正常消息全过滤掉
（该过滤的守卫正是 `!tagsSet.isEmpty()`）；不填 `codeSet` 则 broker 端按 tag 哈希过滤**完全失效**。

### 二、两条钩子（Java `client/hook` + `impl` 源码逐条核对）
- **`CheckForbiddenHook`：异常不吞**（与 Send/Consume 钩子**相反**）。Java 签名就是
  `throws MQClientException`，异常沿 `sendDefaultImpl` 重试链向上 → 这就是「拦截」的实现方式。
  调用点在 `sendKernelImpl` 内、压缩与 sysFlag 之后、SendMessageHook-before 之前，**每次发送尝试
  都调一次**（`retryTimesWhenSendFailed=2` → 钩子被调 3 次），单向发送同样被拦截，上下文**没有**
  `sendResult`。三侧都补了 `register/has/execute` 三个方法。
- **`FilterMessageHook`：异常必须吞掉**（log.error 后继续）且**后续钩子照常执行**；
  `FilterMessageContext.msgList` **可变** → 被摘掉的消息由调用方处置：
  **拉取路径 = 静默跳过**（位点照常推进，不 ack），**POP 路径 = 必须立刻 ack**
  （否则 invisibleTime 到期后 broker 复活重投，表现为「过滤没生效」）。
